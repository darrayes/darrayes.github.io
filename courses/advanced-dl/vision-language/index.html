Vision Transformers and VLMs

How the Transformer you already know reads images, and how it is joined to a language model. Architecture only, built one byte at a time.

·How to use these notes

These notes continue the Transformers notes (§1–58) and the Modern Transformers notes (§59–93), and section numbers continue from there. Anything already taught is cited by its section, for example §17 for the embedding table, and is not taught again. Hover a citation to preview it.

The whole point of these notes is that very little is new. A Vision Transformer is the encoder you already know, fed with a different kind of token. A vision-language model joins that encoder to a language model with parts you have also seen before. Each byte says what problem it solves, shows the equation, explains every symbol, works a small example with numbers, and checks the shapes.

These notes cover the architecture: what the parts are and how data flows through them. How these models are trained is left for later notes.

Part V

Vision Transformers

Turn an image into a sequence of tokens, then reuse the Transformer encoder unchanged.

94Background: An Image as Numbers

Everything a Transformer has done so far starts from tokens: each word becomes an integer ID, then a row of the embedding table (§17). To feed it an image we first need to know what an image is to a computer. It is a grid of numbers.

Pixels and channels. A digital image is a grid of small squares called pixels. A color pixel stores three numbers: how much red, green and blue light it has. Each of these is a channel. Every value is a whole number from 0 (none of that color) to 255 (full intensity). So an image is a 3-D array, a tensor:

I∈ℝHim×Wim×C
Him: image height in pixels (number of rows) · Wim: image width in pixels (number of columns) · C: number of channels, 3 for color (RGB) and 1 for grayscale · xu,v,c: one value, at row u, column v, channel c.
In wordsAn image is Him⋅Wim⋅C numbers arranged in rows, columns and channels.

Intuition. Think of three same-sized spreadsheets stacked on top of each other: one for red, one for green, one for blue. A pixel's color is read from the same cell in all three sheets.

Worked example. A tiny 2×2 color image (a teaching choice):

Pixel (row u, column v)Looks like(R, G, B)
(1, 1) red(255, 0, 0)
(1, 2) white(255, 255, 255)
(2, 1) black(0, 0, 0)
(2, 2) blue-ish(51, 102, 204)

Stored as a tensor, the same image is three 2×2 sheets, one per channel:

Here Him=2, Wim=2 and C=3, so the image holds 2×2×3=12 numbers. For example x2,2,3=204: the blue value of the bottom-right pixel.

Scaling to [0, 1]. Networks work better with small input numbers, so each value is divided by 255:

x~u,v,c=xu,v,c255
x~u,v,c: the scaled value, between 0 and 1 · 255: the largest possible stored value.
In wordsEvery value becomes “what fraction of full intensity”.

The blue-ish pixel (51, 102, 204) becomes (0.2, 0.4, 0.8). Red becomes (1, 0, 0), white (1, 1, 1) and black (0, 0, 0):

Shape checkA standard Vision Transformer input is 224×224 pixels in color: 224×224×3 = 150,528 numbers. Keep this number in mind; the next byte asks what happens if every pixel becomes a token.
Practical noteMany models go one step further and standardize each channel as in §18: subtract a channel mean and divide by a channel standard deviation, using fixed values computed once from a large photo collection. With the commonly used ImageNet values (means 0.485, 0.456, 0.406 and standard deviations 0.229, 0.224, 0.225 for R, G, B), the red value of the blue-ish pixel becomes (0.2−0.485)/0.229 ≈ −1.24, and the whole pixel becomes about (−1.24, −0.25, 1.75). This is a preprocessing convention, not part of the architecture. Libraries also differ in axis order: some store Him×Wim×C, others C×Him×Wim. The numbers are the same, only arranged differently.
Key ideaTo a Transformer, an image is just a block of Him⋅Wim⋅C numbers. The next bytes decide how to cut that block into tokens.

95Why Not One Token per Pixel?

§94 turned an image into a grid of numbers. The simplest way to make tokens would be one token per pixel, with that pixel's C=3 values as the token's input. This byte shows why that does not work, using the attention cost already counted in §75.

Counting the tokens. With one token per pixel, the sequence length is the number of pixels:

T=Him⋅Wim
T: sequence length, as in all earlier notes · Him,Wim: image height and width in pixels (§94).
In wordsEvery pixel is one position in the sequence.

For a standard 224×224 image, T = 50,176 tokens.

Recalling the cost. Each head builds a T×T score matrix (§75), so it stores T2 numbers:

QuantityArithmeticResult
Scores per head5017622,517,630,976 numbers
Memory per head, 2 bytes per number×2 bytes≈ 4.69 GiB
One layer with 12 heads (ViT-Base size, an illustrative configuration)×12≈ 56.3 GiB
Compared with the 4096-token text of §75(50176/4096)2≈ 150× larger

So one small photo would cost about 150 times the score memory of a 4096-token document, in every layer. Even a tiny 32×32 image would already be 1024 tokens.

A second problem: one pixel says very little. A word token carries meaning on its own (“cat”). A pixel token is just three numbers, for example (0.2, 0.4, 0.8): “a blue-ish dot”. That dot could belong to the sky, a shirt or an eye. The meaning is in groups of nearby pixels: edges, textures, parts of objects. With pixel tokens, the first layers would spend their effort just putting neighbouring pixels back together.

Shape checkPixel tokens: T=HimWim tokens, each with only C=3 input numbers. That means very many tokens, each carrying very little. We want the opposite: fewer tokens, each carrying more.
Key ideaPixels make the sequence far too long (the cost grows as T2), and each pixel token means too little. The next byte fixes both at once: group neighbouring pixels into small squares, called patches, and make each patch one token.

96Cutting the Image into Patches

§95 showed that pixel tokens are too many and each means too little. The fix is to cut the image into small squares of P×P pixels, called patches, and to make each patch one token:

N=HimP⋅WimP=HimWimP2
P: patch side, in pixels · N: number of patches, which is now the number of tokens, so T=N · Him/P and Wim/P: number of patch rows and patch columns. The image sides must be divisible by P, which is why images are first resized to a fixed size such as 224×224.
In wordsCount how many patches fit down the image and how many across, and multiply.

Each patch becomes one vector. A patch holds P⋅P⋅C numbers. They are read out row by row into one flat vector xn of length P2C. The patches themselves are numbered in reading order: left to right, then top to bottom. Stacking the N vectors gives the patch matrix Xp, of shape N×P2C.

Worked example. A 4×4 grayscale image (C=1; the values are a teaching choice, 0 = white and 9 = black) with P=2:

N=(4/2)⋅(4/2)=4 patches, each with 2⋅2⋅1=4 numbers:

PatchWherexnLooks like
1top-left[2, 2, 2, 2]flat grey
2top-right[9, 1, 9, 1]dark left, light right: a vertical edge
3bottom-left[5, 5, 1, 1]dark top, light bottom: a horizontal edge
4bottom-right[8, 3, 6, 1]mixed

The real size. For 224×224 color images with P=16: N=14×14=196 tokens, each with 16⋅16⋅3=768 numbers. The score matrix shrinks from 2,517,630,976 to 1962 = 38,416 numbers per head. That is 65,536 times fewer, which is exactly P4=164: T shrinks by P2, and the cost is T2.

Shape checkImage Him×Wim×C → patch matrix N×P2C. No number is lost or created: N⋅P2C=HimWimC. Here 4⋅4=16; for ViT, 196×768 = 150,528, the count from §94.
HedgeP=16 is a common choice, not a rule. A smaller P gives more tokens (finer detail, higher cost); a larger P gives fewer. “ViT-B/16” means a Base-size Vision Transformer with P=16.

97Patch Embedding: One Linear Layer

Each patch is now a vector of P2C raw pixel values, but the Transformer expects tokens of width D (§17). Text solved this with a lookup table. Pixels cannot be looked up, because a patch can take endlessly many different values. Instead, every patch is multiplied by one learned matrix:

Z=XpWpatch+b
Xp: the N×P2C patch matrix (§96) · Wpatch: learned weights, P2C×D · b: learned bias of length D, added to every row · Z: the N×D patch tokens.
In wordsEvery patch gets the same treatment: its pixels are mixed by D fixed recipes (the columns of Wpatch), giving D features.

Link to text. An embedding lookup “picks row k of E” (§17). That is the same as multiplying a one-hot vector (all zeros, with a single 1 at position k) by E. Patch embedding is that same multiplication, with the one-hot vector replaced by real pixel values.

Worked example. Take the four patches of §96, D=3 and b=0. Choose Wpatch by hand so that its three columns have readable meanings. This is a teaching choice, not a trained model:

PatchznReading
1 flat grey[2, 0, 0]some brightness, no edges
2 vertical edge[5, 8, 0]strong left–right difference
3 horizontal edge[3, 0, 4]strong top–bottom difference
4 mixed[4.5, 5, 2]a bit of everything

Check patch 2: brightness =0.25(9+1+9+1)=5; left − right =0.5(9−1+9−1)=8; top − bottom =0.5(9+1−9−1)=0.

HedgeA trained Wpatch is learned, not designed by hand. The original ViT paper reported that its learned patch filters look like simple pattern detectors, somewhat like the ones above, but that is an empirical observation, not a rule.
Shape check(N×P2C)(P2C×D)=N×D. For ViT-B/16, D=768, so Wpatch is 768×768 with 768⋅768+768 = 590,592 parameters. The two 768s are a coincidence: P2C=768 is the patch length and D=768 is the model width.

98Position Embeddings for Patches

Self-attention does not know order (§10): if two tokens are swapped, their outputs just swap too. For images that is fatal. A vertical edge at the top-right means something different from the same edge at the bottom-left. Each patch token must carry where it came from.

The fix is the one BERT and GPT-2 use (§13.1): a learned table with one row per patch slot, added to the patch tokens.

X=Z+Epos
Z: the N×D patch tokens (§97) · Epos: a learned N×D table; row n is the vector for patch slot n, in reading order · X: the N×D input to the encoder.
In wordsEvery patch token gets the stamp of its slot added to it.

Worked example. Hand-chosen slot vectors (a teaching choice): slot 1 [1, 0, 0], slot 2 [0, 1, 0], slot 3 [0, 0, 1], slot 4 [1, 1, 1].

+
=

Why it matters. Put the vertical-edge patch [5,8,0] in slot 1 and it becomes [6,8,0]; in slot 2 it is [5,9,0]. The content is the same, but the input is different, so the encoder can tell the two cases apart.

A subtle point: the grid is flattened. The slots are numbered 1…N in a line. In a 4×4 grid of patches, the patch above slot 6 is slot 2, four places away in the line, while its left neighbour is only one place away. The table does not say “row 2, column 2”. The model has to learn the 2-D layout from data.

HedgeThe original ViT paper reported that 2-D-aware position schemes performed about the same as this simple 1-D table. Many later models use 2-D schemes; those are outside these notes.
Shape checkZ and Epos are both N×D, so they can be added. For ViT-B/16 the table has 196×768 = 150,528 parameters. That is the same as the number of values in one image (§94), because N⋅D=N⋅P2C=HimWimC when D=P2C.
